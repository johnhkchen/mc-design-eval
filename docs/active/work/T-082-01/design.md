# Design — T-082-01 right-sized-model-routing

Three decisions: (A) where the tier seam lives and how it proves the no-API-key invariant; (B) how an
op declares its tier + where the scoping rationale is recorded; (C) the shape of the two detectors.
All grounded in Research.

## A. The per-op model-tier seam

### Options

1. **Add `model` plumbing only.** Every detector resolves its own tier id and passes `model` to
   `requestText*`. *Rejected:* no single seam, the no-API-key invariant has nothing to assert against,
   and the rationale lives nowhere central.
2. **A wrapper on the Agent SDK.** *Rejected outright:* violates the HARD invariant — the SDK path is
   the metered API key. The whole point is to stay on `claude -p`.
3. **A thin `src/model-tier.mjs` seam over the subscription shim (CHOSEN).** A pure `resolveTier(tier)`
   → model id (from `config.MODEL_TIERS`), plus a thin `runTieredOp({tier, prompt, images, …, invoke})`
   that resolves the tier and delegates to `sdk-binding`'s `requestText`/`requestTextWithImage`. The
   invoker is **dependency-injected** (defaults to the shim) so routing is unit-testable without a
   spawn. The module imports ONLY `config.mjs` + `sdk-binding.mjs` — never the SDK package, never
   `ANTHROPIC_API_KEY`.

### Why 3

- One seam = one place the rubric/rationale table lives (`OP_ROUTING`), one place to assert the
  invariant, one place a Phase-2 sweep touches.
- DI keeps the seam pure-testable while the real path is still the metered shim — mirrors how
  `resemblance.mjs` injects its block table to stay pure.

### Proving "the API key never enters this path" (AC #1, a test)

Two complementary tests, because the invariant is both *structural* and *behavioural*:

- **Structural (source guard):** read `src/model-tier.mjs` + the two detector sources and assert they
  contain no `ANTHROPIC_API_KEY` and no `@anthropic-ai/claude-agent-sdk` import. Greppable, matches the
  AC's "test/assert," and catches a future regression that reaches for the SDK.
- **Behavioural (routing):** `runTieredOp` with an injected spy invoker asserts the spy is called with
  `model === resolveTier(tier)` and that the seam constructs no client of its own — the only way it
  reaches a model is the `model` param of the `claude -p` shim. A second assertion confirms the default
  invoker is one of `sdk-binding`'s exported `requestText*` (the subscription functions), not the SDK.

`config.mjs` is pure data, so reading `MODEL_TIERS` pulls in no SDK either.

## B. Tier declaration + scoping rationale

### How an op declares its tier

An op passes `tier: "light" | "strong"` to `runTieredOp`. Each detector module exports its own
`TIER` constant (`"light"`) so the choice is co-located with the detector and single-sourced.

### Where the rationale is recorded (AC #3)

- **`OP_ROUTING`** — a frozen table in `model-tier.mjs`: `[{op, tier, rationale}]`. Single-sourced,
  unit-testable (every entry's `tier` must be a key of `MODEL_TIERS`; every op has a non-empty
  rationale). This is the machine-readable record.
- **`ROUTING_RUBRIC`** — the short rubric string(s) in the same module: *narrow detector / single-view
  classification → light; cross-view judgement, authoring a generator, material zoning → strong.*
- **`docs/active/work/T-082-01/scoping-rationale.md`** — the written deliverable, generated by the
  runner from `OP_ROUTING` + `ROUTING_RUBRIC` so the doc and the code can't drift. Records both
  detectors (light) plus the two contrasting strong-tier ops named by the rubric (the *seal* authoring
  and material zoning) as worked examples.

Decision: keep the table in code (testable, single-sourced) and **render** the markdown from it, rather
than hand-maintaining prose — same discipline as the version-pinned config.

## C. The two detectors (each scoped to one view)

Both follow the `resemblance.mjs` split: a PURE core (geometric prior + fixed prompt + parser) in
`src/view/`, the metered light-tier call in the runner. Output is plain-text JSON (via
`requestTextWithImage`), parsed with the existing `stripToJson` then shape-validated.

### Roof-patch detector (`src/view/roof-patch.mjs`, tier = light)

- **View:** the roof — `roofRegion(occ)` (top `+y` surface) + the `top` render.
- **Geometric prior (pure):** `roofCandidates(roofRegion)` → dominant roof block, list of `stray`
  cells (block ≠ dominant), and `holeCount` (from `coverage < 1` over `area`). Bounds the model's job
  to *confirm/triage* a small candidate set rather than scan 6429 voxels.
- **Prompt (pure, fixed):** `buildRoofPatchPrompt(roofRegion, candidates)` — states dominant material,
  coverage, the candidate strays/holes, and asks for cells that genuinely read wrong, seeing the top
  render.
- **Parser (pure):** `parseRoofPatch(text)` → `{schema, patches:[{x,z,issue,note}]}` where `issue ∈
  {stray-material, hole, wrong-tone}`. Drops malformed rows; throws only on non-JSON.
- **Why light:** narrow classification on ONE view over a bounded candidate set — the rubric's "light"
  case exactly.

### Hollowable-mass detector (`src/view/hollowable-mass.mjs`, tier = light)

- **View:** the massing — `footprint` + `storeyBands` + `wallFields` (skin holes) + a `threeQuarter`
  render. Feeds T-080-01.
- **Geometric prior (pure):** `hollowableCore(occ)` → count of fully-enclosed interior voxels (all 6
  neighbours occupied = safe-to-carve bulk), grouped per storey band, plus total skin-hole count
  across faces (a hole means the shell is NOT watertight → seal before hollow).
- **Prompt (pure, fixed):** `buildHollowablePrompt(read, core)` — footprint dims, storey bands,
  enclosed-core size per band, skin-hole count; asks the model (seeing the 3/4 render) to confirm the
  hollowable regions and FLAG blockers (any skin hole).
- **Parser (pure):** `parseHollowable(text)` → `{schema, hollowable:boolean, regions:[{yStart,yEnd,
  inset,note}], blockers:[string]}`.
- **Why light:** bounded geometric classification scoped to footprint+bands. **Recorded caveat for the
  rubric:** if `blockers` is non-empty (skin holes), *authoring the seal* is a cross-view generative op
  → strong tier (S-084). The detector that *finds* the blocker is light; the generator that *fixes* it
  is strong. This contrast is the rubric's worked example.

## What is explicitly NOT in scope

- Applying patches / performing the hollow (S-079, S-080 own the mutation). These detectors only
  *read* and emit a target.
- Per-call cost accounting beyond noting the calls are metered + the tier used.
- Any change to `requestText*` argv (the `--model` plumbing already exists) — the seam only *chooses*
  the id.
