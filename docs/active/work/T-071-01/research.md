# T-071-01 — llm-material-map · Research

Epic **E-21**. Goal of this ticket: a **multimodal BAML function** that takes the **concept image +
design doc** and emits a structured **material map** — `[{ role, block, placementRule }]` — that
*preserves near-tone-distinct materials* (the stone_bricks-vs-cobblestone collapse that mean-color
CIE-Lab matching merges). This is E-21's "define style" step; it runs *after* E-19's cleanup.

This is **descriptive** — what exists and where, the seams to hook into. No solutions here.

## 1. The failure this fixes (the prior)

Mean-color matching (`nearestLab`, `src/color/cielab.mjs`) collapses materials that are visually
distinct but tonally near — **stone_bricks (L≈ grey) and cobblestone (L≈ grey)** map to the same
nearest block. The block→Lab table (`src/color/block-lab-table.json`, 305 survival blocks) has all
four gatehouse materials present and distinct as *ids* (`stone_bricks`, `cobblestone`,
`deepslate_tiles`, `dark_oak_log` — verified), but the **color metric** cannot tell the greys apart.
Material identity is **semantic**, not chromatic — see memory `material-identity-is-semantic`. So the
fix is to let a multimodal LLM *see the concept* and *name* the material per feature/region.

    `benchmarks/sculpture/glb/stone-gatehouse.glb`.

## 3. The BAML seam (where this function lives)

BAML functions are **rendered to text** (`b.request.*`), piped through `claude -p` (subscription),
and the reply **SAP-parsed** (`b.parse.*`). `ClaudeStub` (`baml_src/clients.baml`) is never actually
called — it only shapes `.request`. The TS client is generated into `baml_client/` by
`npm run baml:gen` (`baml-cli generate --from baml_src`).

Existing functions and their files:
- `baml_src/judge.baml` — `JudgeFacade(brief, render: image) -> FacadeScore` — **multimodal**
  (image input), enum-constrained categorical output. The closest sibling: small structured output,
  image in.
- `baml_src/review.baml` — `DiagnoseFacade(brief, render: image) -> FacadeDiagnosis` — multimodal,
  a **list** output (`FacadeDefect[]`). The structural sibling for a list-of-records result.
- `baml_src/facade.baml` — `BuildTempleFacade(brief, design_doc) -> TempleFacade` — text-only build
  fn; shows the **op-tagged class** + `manifest string[]` palette idiom and `@description` usage.
- `baml_src/conceptart.baml` — `Facade/Sculpture/BuildingConceptPrompt(design_doc, target_blocks,
  attached) -> string` — text-prompt-only (image generated by Nano Banana downstream).

**The bridge pattern** (`.mts` run via `npx tsx`, stdin job → stdout JSON):
- `src/sculptor/baml-review.mts` is the canonical multimodal bridge. It: reads `{imagePath, brief}`,
  base64s the image, `Image.fromBase64(mediaType, b64)` (from `@boundaryml/baml` default export —
  CJS), `b.request.DiagnoseFacade(brief, Image…)`, extracts the text block + image block from
  `req.body.json().messages`, calls `requestTextWithImage({prompt, images, model})`
  (`src/sdk-binding.mjs:478`), strips fences/`{…}`, `b.parse.DiagnoseFacade(cleaned)`, maps the enum,
  writes `{defects}` to stdout. **This is the template to copy.**
- `benchmarks/sculpture/baml-concept.mts` shows the multi-image `images` attach path and the
  `variant`-switch over `b.request.*`.
- `benchmarks/temple-facade/baml-judge.mts` / `baml-build.mts` — the original judge/build bridges.

`requestTextWithImage({ prompt, images, model, effort, system, onMessage })` →
`{ text, … }` (subscription `claude -p`, multimodal). `PHASE1_MODEL_ID` / config in `src/config.mjs`.

## 4. Block-vocabulary validation (the AC's "validated against the artifact vocabulary")

Two layers:
- **Shape** (`src/artifact.mjs` → `schema/design-artifact.schema.json`): a block id is
  `^[a-z0-9_.-]+:[a-z0-9_]+$` (namespaced). The schema validates *shape only* — "whitelist membership
  is checked by the palette validator (E-04), not here".
- **Membership / vocabulary**: the real survival-block set is the 305-row block→Lab table
  (`src/color/block-table.mjs` → `loadBlockTable()` → `{ blocks:[{block, texture, rgb, lab, var}] }`,
  keys are **bare**, e.g. `stone_bricks`). `src/sculptor/material.mjs` owns the **namespace boundary**
  helpers `tableKey(id)` (strip `minecraft:`) and `blockId(key)` (add it back). `material-segment.mjs`
  has `offPaletteCount(keys, palette)` and `paletteKeySet`. `glb-voxel-build.mjs` has
  `paletteFromManifest(manifest, table)` and `assertPaletteDiscipline(artifact, palette, {cap})`.

So "real survival block" = `tableKey(block)` is present in `loadBlockTable().blocks`. This is the
membership check the pure module must run. The **design-doc palette is the prior, NOT a cap** (AC) —
the map may *add back* blocks the tight palette dropped, as long as each is a real table block.

## 5. The PURE / LIVE split (the project's load-bearing idiom)

Every model-touching module splits a **PURE core** (unit-tested by `node --test "src/**/*.test.mjs"`,
no GL/network/`claude -p`/`Date`/`random`) from **LIVE leaves** (spawned tsx + metered `claude -p`,
NOT unit-tested). Examples: `src/sculptor/review.mjs` (pure `routeDiagnosis` + live `defaultDiagnose`),
`src/form/material-segment.mjs` (pure `segmentMaterials` + impure `segmentMaterialsGlb`),
`src/form/e19-cleanup.mjs` (pure assembler) + `benchmarks/sculpture/e19-build.mjs` (impure runner).

**AC#5 maps onto this directly:** "Pure parse/validate logic unit-tested; the live multimodal call is
metered." So: a pure `src/form/material-map.mjs` (parse the model's raw reply → validate roles/blocks/
placementRules → normalized map) + a live bridge (`.mts`) + an impure runner that writes the saved maps.

## 6. The output contract (`placementRule` vocabulary)

AC names the feature/region vocabulary: **walls / corners-edges / roof / base / trim / openings**.
This is a *fixed enum* the map's `placementRule` draws from — the consumer (E-21's downstream
assign-by-geometric-feature, *not this ticket*) will map each rule to a geometric selector. This
ticket only needs to **define + validate** the vocabulary, not consume it. Each entry:
`{ role: string (free-text material intent, e.g. "structural walls"), block: namespaced real survival
block, placementRule: one of the enum }`.

## 7. Runner / artifact-output conventions

Benchmarks runners live in `benchmarks/sculpture/*.mjs`, write under
`benchmarks/sculpture/<name>/<subject>/…`. AC wants `benchmarks/.../material-map/<subj>.json`. Runners
import pure cores + impure leaves, `spawn` the `.mts` bridge (`npx tsx`), and a matching `npm` script
is added to `package.json` (cf. `"e19:build"`). `--offline` flags are common for rebuilding reports
from committed outputs without a live call.

## 8. Constraints & assumptions surfaced

- **Cottage has no design doc** — must be resolved (Design): tolerate-missing vs author-a-doc.
- The **live call is metered** — `npm test` must pass with **zero** live calls; the saved maps are a
  separate (metered) run. Prior E-19 tickets *did* run live sweeps successfully in-session via the
  `claude -p` subscription, so a live material-map run is expected to be feasible.
- `baml_client/` is **generated** — adding a BAML function requires re-running `npm run baml:gen` and
  committing the regenerated client (the repo commits `baml_client/`).
- The map **defines E-21's allowed palette** — downstream (not here) consumes it; so the output must
  be self-describing and stable (a clean JSON the next ticket can read without re-deriving).
- Keep the new BAML fn **separate** from the frozen judge/build/concept fns (the project's "keep
  prior runs reproducible" rule — every concept variant is a new function, never an edit).
