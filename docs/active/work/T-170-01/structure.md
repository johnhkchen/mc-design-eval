# T-170-01 Structure — emit-typed-kind-from-layer-a

File-level blueprint. No code here — the shape of the change, the ordering, the interfaces touched.

## Files MODIFIED

### 1. `baml_src/department.baml` — the contract + prompt (the heart of the change)

**1a. `class CritiqueItem`** — add one field between `missing` and `severity`:

```
  kind "add" | "replace" | "remove" @description("add = element absent; replace = present but WRONG style/material; remove = an element that should not be there")
```

Field order after edit: `department, expected, present, missing, kind, severity`. The
`@description` text is the blueprint's verbatim wording.

**1b. `function DiagnoseBuild` prompt** — add one tagging sentence in the per-item instruction
paragraph, after the "...what is absent versus expected (missing, empty if nothing missing)."
clause and before the department-tagging sentence:

```
Also tag each item with its kind: add if the element is absent (present is empty), replace if
something is present but in the WRONG style/material, remove if an element is present that the style
does not want.
```

No other change to this file. The header comments (E-39 hard rules, S-163 decision) already
describe the add/replace/remove vocabulary — no comment edit required, though a one-line note that
`kind` now makes that vocabulary judged is optional and harmless.

## Interfaces / contracts

- **Producer:** `b.parse.DiagnoseBuild(text)` now yields items carrying `kind`. The rendered prompt
  instructs the live judge to emit it.
- **Consumer:** `itemStyleClass(item)` (unchanged) short-circuits on `kind` before the structural
  fallback. No new consumer is introduced.
- **Back-compat:** items without `kind` (legacy committed critiques) still classify via the
  structural triple read — the fallback path is retained, not removed.

## Ordering of changes (matters)

1. Edit `department.baml` (schema field + prompt line).
2. `npm run baml:gen` (regenerate the BAML client) — required before any render/parse reflects the
   new field.
3. Regenerate `diagnose/prompt.golden.txt` via a bridge render.
4. Edit the four fixture JSON/txt files (diagnose + critique-contract) to add `kind`.
5. Strengthen FX-DB2 in `fixtures.test.mjs`.
6. `npm test` — full green, including transport-guard and the frozen-instrument suites.

Steps 1-2 must precede 3 (the render reflects the schema). Steps 3-5 are independent of each other
once 2 is done. Step 6 is the gate.
