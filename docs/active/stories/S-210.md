## Context (self-contained)

Epic **E-54**, the ergonomic fix the arch work exposed. Today the aperture hand widens the gate **wherever the
build already has a slot** — `carveTargetCells` (`src/view/aperture-carve.mjs:61`): *"the EXISTING aperture (the
build positions the slot); width from the program."* So whether the gate ends up **centered** on its wall face
depends on where a pre-existing (often GLB-inherited) void happened to sit, not on intent. A gatehouse gate that
sits off-center, or that can only go where a stray void is, reads wrong and makes the arch hand awkward to drive.

The fix: make centering a **first-class, by-construction** operation. A **center-on-face** helper — given a
declared wall face (the footprint edge for the opening's `dir`) and an opening width — computes the opening's
column span **centered on the face** (`uLo = floor((faceW − w)/2)`), independent of any existing slot, and feeds
it to `rebuild_arch` (and `carve_arch`). A centered wide arch reads as a proper gatehouse gate.

## Falsifiable claim (anti-hedge — lead with how it fails)

A declared gate is placed **centered on its wall face by construction** (column span computed from face width,
not inherited from a stray slot), reads centered on the glance from the front azimuth, and passes the
aperture-coherence gate. **Fails if:** forcing a centered span **conflicts with the GLB-inherited slot** (the
old void remains beside the new centered opening → a double opening / ragged edge — then centering requires the
inherited slot be *removed/rebuilt* first, not overlaid; name it); the face width is **ambiguous** on a
near-square footprint (which edge is "the front"? — tie to the recognition-declared front/gate, the E-50
orientation finding); or centering moves the opening off a structural support the wall needs (the lintel can't
span at center — unlikely at this scale, but check).
