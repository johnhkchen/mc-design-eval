# The design backlog — drafts, not tickets

This directory is the output tray of the **design-backlog factory** (E-32, S-131): brush
work-item **drafts** generated by `DecomposeBrushBacklog` from a formed style + the current
brush registry. **Lisa never scans this directory** — `.lisa.toml [dirs]` lists only
`docs/active/tickets`, `docs/active/stories`, `docs/active/work`, and
`src/factory/backlog.test.mjs` (B5) asserts `docs/active/backlog` stays outside them. Drafts
also carry none of lisa's scheduling vocabulary (no `id`/`story`/`phase` — B9), so a draft
cannot enter the DAG even by accident. **The system never schedules its own work** (E-32 Rule 3).

## What lives here

- `<style>--<brush-name>.md` — one draft per genuinely-new brush: purpose, parameter sketch,
  composition notes, test plan, preview subject, self-contained Context + Acceptance Criteria
  (the T-128 brush-contract dimensions, ready to become a ticket body).
- `<style>--parametrization-notes.md` — needs an **owned** brush already covers (parametrize,
  never duplicate), plus any code-gate demotions and hand-check warnings.
- `records/<style>/` — the run's committed evidence: inputs, rendered prompt, T-114 ledger
  (full raw replies), parsed+deduped backlog. Drafts are byte-replayable from these:
  `node scripts/design-backlog.mjs --pack packs/<style>.json --offline`.

Generate: `node scripts/design-backlog.mjs --pack packs/<style>.json`
(or `npm run backlog:generate -- --pack …` — keep the `--`, npm swallows flags without it).

## Promotion — the only path to scheduling, and it is human

A draft becomes work **only** when a human (or the planner under explicit user direction —
never the factory, never a build session) promotes it:

1. **Review** the draft. Edit freely — the draft is a starting point, not an order. Check the
   registry first: if an owned brush now covers the need, move the content to the notes file
   instead of promoting.
2. **Assign** ticket identity: an `id` (next free `T-NNN-NN`), a `story` (existing or new
   `S-NNN`), `priority`, `type: task`, `status: open`, `phase: ready`, `depends_on` as needed.
3. **Move** the file to `docs/active/tickets/<id>.md`, reshaping the frontmatter to the house
   ticket format (the body sections already fit). Record the promotion in the draft's
   `promotion:` block *in the ticket's git history* (promoted_by, date, source draft).
4. Lisa picks it up from there like any ticket.

## The rework log — the factory's quality metric

The measure of a draft is that it runs through lisa **without rework**. After a promoted
draft's ticket completes, record the outcome here (and in the promoted ticket's `rework:`
field): `none` is the target and a legitimate entry.
