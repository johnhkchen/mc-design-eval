# Review — T-081-01 nxm-floorplan-infill

Handoff for a human reviewer. What changed, how it's tested, what to watch.

## What this delivers

The **program path crossing into design** (E-23 / S-081): the empty T-080 hollow shell is **filled with an
N×M grid floorplan** across its storeys, generated by a program the **LLM authors/steers** from the
below/plan view. The interior has **no reference**, so the gate is **plausibility**, not resemblance. The
split is the project's program-author seam (`hollowable-mass.mjs`):

- the **metered, strong-tier** `floorplan-author` call returns a small `FloorplanSpec` (rows, cols,
  materials, doorPolicy, frontDoor) — the floorplan **reasoning** (the rubric's "authoring a generator");
- a **pure generator** partitions the footprint and **places the bulk** — floors at the storey lines,
  dividing walls on the grid, interior doorways by **exclusion** (no air op);
- a **pure plausibility gate** scores six hard constraints + a **named residual** (Rule 7).

## Open concerns / notes for the reviewer

1. **The headline residual — perspective renders are NOT byte-identical, and cannot be.** The **exterior
   shell surface is provably unchanged**: the 10-camera lattice digest (6 ortho + 4 diagonal) is held — **0
   surface cells differ**, and the runner *throws* if it ever isn't. But the benchmark renders are
   **perspective** (FOV) at slight elevation, so off-center pixels see *through the shell's real door/window
   openings* into the new interior (the front camera looks down the front door). Measured deltas: **front
   0.41% / top 0.056% / 3-Q 0.049%** of pixels, all interior-through-openings. Byte-identical renders are
   **impossible** for any non-trivial floorplan behind a front door — seeing a room through an open door is
   correct, not a defect. The interior is gated by **plausibility**; the exterior **resemblance** is
   protected by the lattice digest. This is the named exterior-side residual (Rule 7), recorded in
   `floorplan-report.json.renderResidual`.
2. **`openings()` returns `[]` on the cottage → the gate's `openingsAlignShell` is the in-gate named
   residual.** The front-most ortho march hits the outer skin everywhere (recessed/glazed doors read as no
   hole), so interior-door↔exterior-door alignment is **steered** (the LLM's `frontDoor`, here `-z` u=13),
   not geometrically verified. Reported `pass:true` + the residual string, never a silent green. A future
   ticket could read openings from a *depth* pass to verify alignment geometrically.
3. **The fill-safety predicate, not slice-enclosure, is load-bearing.** `interiorColumnsAtY` (2-D slice)
   is only the room-air heuristic; `isFillHidden` (front-occlusion from all 10 lattice cameras) is the
   guarantee. The first live run threw on a slice-enclosed-but-visible cell — the invariant caught it. A
   reviewer changing the placement logic must keep every placement gated by `isFillHidden`.
4. **Reachability is per storey; there is no stair.** The AC's "a path / doors connect them" is satisfied
   within each storey (spanning doorways → connected room graph). Vertical circulation between storeys is a
   plausible next step, not in scope.
5. **The author is non-deterministic across runs** (Opus returned 2×2 / 3×3 / 2×3 on successive runs — all
   gate-passing). The generator + gate are deterministic given a spec; only the steering varies. A `seed`
   would pin it for a Phase-2 sweep.
