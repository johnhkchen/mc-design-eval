## Open concerns / known limitations (named)

1. **Bumps remain** — the contract has no delete, so the ragged ridge keeps ~218 cliff joints
   (smoothness 0.827, not ~1). The top render reads substantially cleaner; full course regularity needs
   the E-25 concept-derived full-shell reshaping.
2. **The side wall's large timber patches survive** the strip — they are genuinely connected multi-cell
   components (the GLB splat laid them as fields, not specks), so the run/line rule keeps them. That is
   a SPLAT-QUALITY issue upstream (what the splat paints), not a pattern-strip miss; if S-089 wants them
   gone, the lever is the splat palette/coverage, not a looser strip (which would start eating studs).
3. **2-cell legit details strip** under minKeep=3/minExtent=3 (e.g. a 2-cell sill). Parameters are data;
   the record's byZone/byBlock breakdown makes any wrong strip visible. Eyeball check found no lost
   feature on the cottage (chimney, studs, trim all intact).
4. **Eave-edge notches that drain are not raised** (they are outlets, not basins) — part of the honest
   residual in concern #1.
5. **The pass is not yet in the spray:paint pipeline** — deliberate (T-088 owns gate wiring, T-085's
   runner is shared turf; T-086 set the sibling-runner precedent). E-24 Rule 1 is satisfied at the
   `pattern:cottage` level (one command reproduces everything end-to-end); folding the ops into the
   spray pipeline is S-089/E-25 consolidation work.
6. **Zoning is derived from the INPUT build** and reused for the post-fill strip; raised cells classify
   "roof" by geometry (y ≥ upperTop), so no drift — but if a future subject's fill raised columns below
   upperTop, the single-zoning assumption would need a re-derive.
7. **Mid-implementation race observed**: T-088-01 committed to zone-fill.mjs between my read and edit
   (`1e74bc9`). Resolved by re-read; the edits are disjoint and both suites pass together. Flagging per
   the workflow's missing-DAG-edge rule: three E-24 tickets now touch zone-fill.mjs serially — fine so
   far, but a future story splitting that module should add explicit dependency edges.
