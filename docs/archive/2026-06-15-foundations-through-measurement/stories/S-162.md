## Context (self-contained)

Epic **E-38**. The price-of-admission leg: the agent must climb across **many** kinds of builds,
unattended — not 3 hand-tuned subjects. The 2026-06-15 diagnosis
(`experiments/eval-alignment/DIAGNOSIS-multimass-and-volume.md`) shows this is **the same fix** as
unsticking the cottage (S-160): the autonomy loop hardcodes a `SUBJECTS` map (eave/ridge/material per
subject) that the recognition program already emits. Volume is blocked by that hand-authoring, not by the
agent's tools.

This story removes the per-subject hand-authoring and proves the climb generalizes on subjects the loop
was **not** tuned for.

## Falsifiable claim (anti-hedge — lead with how it fails)

Once S-160 lands recognition-driven construction, **deleting the `SUBJECTS` map and feeding the loop only
recognized programs** will let it climb subjects it was never hand-tuned for — at least **N≥6** subjects,
unattended, with a positive defect-eval delta on the majority. **It fails if:** new subjects need
per-subject code after all (then the constants weren't really removable — name what still must be
hand-set); OR the climb only works on the original 3 and collapses on fresh subjects (then the tools
overfit the tuned set — report the failure rate per subject); OR most subjects have no recognition program
and producing them is the actual bottleneck (then *recognition throughput*, not construction, is the
volume gate, and that is the finding). Report the per-subject ledger regardless of where it lands.

## Measured volume ceiling (2026-06-15 probe — `DIAGNOSIS-multimass-and-volume.md`)

The recognition runner (`benchmarks/sculpture/recognize.mjs`) is **already registry-driven, not
per-subject code** — `subjectDefs()` filters `durable-skin.mjs` `SUBJECTS` for `glb && generated.scale`,
with a self-grep forbidding subject keys in the runner. So recognition *throughput* is not the wall; the
wall is two concrete, measured layers:

1. **Roster size = 4** (cottage, barn, church, gatehouse) — all 4 have GLB + concept and are recognizable.
   "Many kinds of builds" needs the roster to **grow**, which means new subjects fed through the existing
   image→3D path ([[trellis-glb-path-works]]) + a concept + a registry entry. That intake is the real
   breadth lever.
2. **Recognition coverage is incomplete within the 4**: only 3 programs exist on disk (cottage, barn,
   barn--saltcrag); **gatehouse and church have NO committed program**. Gatehouse is currently in the
   autonomy loop on *faked constants* — so deleting `SUBJECTS` (the S-160 corollary) **drops gatehouse**
   unless it is recognized first. Recognizing gatehouse + church is the cheap immediate win (one
   `recognize` run each — model spend, so it belongs to this story's ticket, not a side-run).

## Tickets (to be cut after S-160 proves multi-mass construction)

- **Recognition coverage of the existing roster:** run `recognize` for gatehouse + church (they lack
  programs); confirm `recognize:offline --all` reproduces all 4 byte-identically. This makes the current
  roster honest before any `SUBJECTS` delete.
- **Delete the `SUBJECTS` map;** drive the loop purely from `<subject>.program.json`. Re-run the batch
  across all 4; record the honest per-subject climb ledger + a render strip.
- **Breadth (the actual "many"):** add ≥2 fresh subjects via the image→3D intake (new GLB + concept +
  registry entry, no per-subject code) and show the loop climbs subjects it was never tuned for. This is
  where the falsifiable claim is really tested — the original 4 are not "many."
